## 一、结论摘要

- 所有最终有效用例均实现 `100%` 记录成功，未出现丢失、重复、Flink 作业失败或重启。
- 固定 `6,000 msg/s` 时，并行度 1/2/4 的端到端吞吐约为 `5.49k msg/s`，差异小于 `0.2%`，说明该阶段主要受生产速率限制。
- `50,000 msg/s` 高压用例中，端到端吞吐约为 `43.5k–43.7k msg/s`；并行度 4 的平均延迟和 P99 低于并行度 1，但吞吐差异仍受生产窗口和测量窗口限制。
- 固定并行度 4 时，单 TaskManager×4 slots 的 P99 为 `25 ms`、Checkpoint 平均 `5.4 ms`；4 个 TaskManager×1 slot 的 P99 为 `84 ms`、Checkpoint 平均 `54.8 ms`。
- 并发作业从 1 增至 4 时，聚合端到端吞吐从 `5.08k` 增至 `20.25k msg/s`，P99 从 `50 ms` 增至 `66 ms`，积压峰值从 `29,046` 增至 `94,026`，作业失败率和记录失败率始终为 `0%`。
- VMware Workstation MCP 已配置；客户机执行开关仍为 `VMWARE_ENABLE_GUEST_EXECUTION=false`，未把登录密码写入源码、配置或本报告。

### 指标定义

- **端到端吞吐**：唯一成功输出记录数 ÷ 测量窗口秒数。
- **端到端延迟**：消息生成时间到输出 Topic 消费时间，报告平均值、P95、P99。
- **记录失败率**：缺失输出数 ÷ 期望输出数。
- **作业失败率**：状态为 `FAILED` 或异常历史非空的作业数 ÷ 总作业数。
- **Kafka 积压**：同一采样时刻所有 Flink consumer group 已提交 offset 的 `LOG-END-OFFSET - CURRENT-OFFSET` 之和；最终值在 Checkpoint 提交后采集。
- **CPU、内存、磁盘 I/O**：Windows 宿主机全局计数器，每秒采样；内存为总可见内存减可用内存，磁盘为 PhysicalDisk Total 字节速率。
- **Checkpoint 耗时**：Flink REST 返回的 `end_to_end_duration`，单位 ms。

## 五、单 TaskManager 与多 TaskManager 对比

两组均为并行度 4、`60,000` 条、`6,000 msg/s`；唯一变量为 TaskManager 布局。

| 布局 | 端到端吞吐 (msg/s) | 平均延迟 (ms) | P95 (ms) | P99 (ms) | Checkpoint 平均/最大 (ms) | 记录失败率 |

| 4 TM×1 slot | 5,297.95 | 9.07 | 18 | 84.00 | 54.80 / 247.0 | 0% |

**结论**：本机同进程组环境下，单 TM×4 slots 更适合当前 Kafka-Flink 作业；多 TM 布局引入额外 RPC、调度和跨进程开销，P99 和 Checkpoint 最大耗时明显变差。该结论针对当前 Windows 单机配置，不直接外推到独立节点集群。

**结论**：

- 并发作业数增加后，聚合吞吐近似线性扩展，但 P99 和积压持续上升。

- 2 作业用例的系统磁盘计数器出现 `941.15 MB/s` 峰值，属于宿主机全局 I/O（含 Kafka、日志和缓存），不能直接归因于单个 Flink 作业。
- `kafka-flink-concurrent-2.json` 是修复多输出提前退出条件前的预检结果，未纳入结论；正式结果使用 `kafka-flink-concurrent-2-fixed.json`。

## 七、总体判断与限制

1. 当前作业链路稳定：所有最终有效用例均 `0` 记录失败、`0` 作业失败、`0` Checkpoint 失败。
2. 单 TM×4 slots 在当前单机环境中优于 4 TM×1 slot，尤其是尾延迟和 Checkpoint。
3. 资源指标是宿主机全局值，包含 Kafka、ZooKeeper、前后端和其他 Java 进程，不能当作 Flink 进程独占资源。
4. 6k 固定速率用于低负载基线；50k 用于高压观察，但尚未完成真正的饱和拐点扫描。
5. 本报告未执行 Ubuntu 客户机内发压；需取得客户机用户名并确认快照、防火墙和网络隔离后，才能安全开启客户机执行。
